# Performance

The architecture's performance properties are structural: normalization,
batching, and subscriber-aware eviction do the heavy lifting. This page maps
each mechanism to its knob.

## Renders

- **One write, one render.** A mutation updates the graph once; subscribers
  re-render once. There is no cascade of component-to-component updates
  because there is no sideways data flow.
- **Realtime coalescing.** The
  [RealtimeManager](/docs/guides/concepts/realtime-batching) collapses a 16 ms
  burst into one Zustand write. Do not set `flushInterval: 0` in production —
  unbatched mode exists for tests.
- **Fine-grained bindings.** Solid mirrors graph state field-by-field; Svelte
  5 runes track property access. Lists re-render rows, not pages.

## Network

- **Deduplication** collapses concurrent identical fetches into one request.
  Mount ten subscribers to the same entity; pay for one fetch.
- **SWR** serves cached data instantly and revalidates in the background.
  Tune with `staleTime` per query and `defaultStaleTime` globally:

```ts
import { configureEngine } from "@prometheus-ags/entity-graph-core";

configureEngine({
  defaultStaleTime: 30_000,
  revalidateOnFocus: true,
  revalidateOnReconnect: true,
});
```

- **Detail hydration** reuses the entity already fetched for the list row —
  opening a detail view costs one fetch for the *missing* fields, not a full
  duplicate record.

## Lists and sorting

- **Binary-search insertion** places realtime arrivals in sorted position in
  O(log n) instead of re-sorting the list.
- **`applyView`** evaluates filters/sorts over IDs and joins against the
  graph at render time — no intermediate arrays of copied entities.

## Memory

- **Subscriber-aware GC** evicts entities with zero subscribers after
  `defaultGcTime` (default 5 min). Lists protect the entities they reference.
  Start the collector once:

```ts
import { startGarbageCollector } from "@prometheus-ags/entity-graph-core";

const stop = startGarbageCollector(); // default 60 s sweep interval
```

- **Patches are shallow.** UI-only overlays store only the patched fields,
  merged at read time — selection state on 10 000 rows costs 10 000 small
  objects, not 10 000 entity copies.

## Measure before tuning

Gate optimization work on measurement: the browser DevTools performance
panel and the [event bus](/docs/guides/concepts/devtools) (event rate,
burst coalescing) tell you whether renders, network, or memory are the
actual bottleneck. Do not reach for `flushInterval: 0`, manual memoization,
or custom caches without a measured problem — each one trades away a
structural guarantee.
