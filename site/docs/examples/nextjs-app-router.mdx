# Tutorial: Next.js App Router

`examples/nextjs-app` proves the SSR slice of the contract: concurrent server
requests stay isolated, and hydrated client graphs never duplicate a fetch
inside `staleTime`.

## Architecture

The React binding supports provider-owned graphs, which are required during
server rendering so concurrent requests never share entity state. The example
therefore splits the world:

- **Server:** `src/lib/server/request-graph.ts` mints a fresh graph per
  request with the core's `createGraphStore()`. A release contract test
  statically guards that server modules never write the global store.
- **Handoff:** the RSC page prefetches into the request graph, dehydrates a
  serializable payload (entities + list slots keyed by `serializeKey`), and
  renders data HTML directly from it.
- **Client:** `RequestHydrationBoundary` renders an identical shell on server
  and first client pass (no hydration mismatch), writes the payload post-mount
  with freshness stamps, then mounts graph-reading children.

The client-owned `GraphHydrationProvider` also mounts a development-only
`NextEntityGraphDevtools`. That client component checks
`process.env.NODE_ENV`, dynamically imports the side-effect-free `./devtools`
entry after hydration, and passes the same provider-owned store to
`EntityGraphDevtools`. No launcher markup is emitted by the server and the
ordinary package root remains inspector-free.

The inspector subpath is available from the published npm `3.2.0` package.

## Setup

```bash
pnpm install
pnpm run dev:next
```

Open `http://localhost:3000` (redirects to `/dashboard`); the certified SSR
route is `/release-showcase` (`force-dynamic`).

## Deployment and platform notes

A standard Next.js production build (`pnpm run build:next`). The key
deployment rule: **never write the global graph during server rendering** —
keep server data flow behind per-request `createGraphStore()` instances and
hand data across with the hydration boundary.

## Troubleshooting

- **Hydration mismatch warnings:** the boundary must render the identical
  shell before mount; do not read graph state during the first client pass.
- **Duplicate fetches after navigation:** the hydration payload carries
  freshness stamps; if you bypass it, SWR treats the entities as unfetched.
- **Data leaking between requests in dev:** a server module imported the React
  binding's global store — the release contract test catches exactly this.
