    Class Catalog<T, F>

    Collection of available components and functions.

    The F parameter distinguishes catalogs that carry executable function implementations (FunctionImplementation, the default and the only kind a renderer should hold) from schema-only catalogs (FunctionApi), whose functions are signatures loaded from catalog JSON with no code attached. Consumers that need to execute functions, such as NodeResolver, constrain F to FunctionImplementation so a schema-only catalog is rejected at compile time rather than resolving values to undefined at runtime.

    A catalog is its catalog document in model form. An entry fromJson loaded (JsonComponentApi, JsonFunctionApi) has its JSON Schema definition as its model, from which its Zod schema is derived. An entry defined in code has its Zod schema as its model; when the schema is annotated as a specification model (see spec), as the built-in basic catalogs' generated models are, toJson computes its definition in the layout of the catalog's protocol version, and otherwise generates one. The catalog keeps the document-level fields (CatalogDocumentOptions). toJson assembles the document from all of these and validationSchema bundles it, so Catalog.fromJson(doc).toJson() equals doc, and toJson of a built-in basic catalog equals its published document.

    derive

    • derive(options: DeriveCatalogOptions<T, F>): Catalog<T, F>

      Returns a new catalog, under its own ID, built from entries of this one and new entries.

      In components and functions, a name keeps this catalog's entry of that name, and an entry adds it, or replaces this catalog's entry of the same name. Leaving either list out keeps all of this catalog's entries of that kind. The new catalog keeps this catalog's version, theme and the document-level fields that describe its layout, and drops defs that only entries left out referenced, as withEntries does.

      It does not keep this catalog's $id, title, description or instructions, which describe this catalog: instructions often name its ID and its components in their examples, so they would teach a model to write messages for the wrong catalog.

    toJson

    • toJson(): Record<string, unknown>

      Returns the unbundled catalog document for this catalog, assembled from its model and memoized.

      The document-level fields come from the catalog (CatalogDocumentOptions). An entry fromJson loaded is written as its definition, with references kept as written, unless it references a local definition the catalog lacks. An entry defined in code whose schema is a specification model is computed from its model in the layout of the catalog's protocol version, with its mixins and the defModels written to $defs; any other entry is generated from its Zod schema. Common types references are written against commonTypesUri. The anyComponent and anyFunction unions are computed from the entries. So for a catalog loaded with fromJson, the result equals the loaded document (minus any entries that the document's anyComponent.oneOf or anyFunction.oneOf unions omit, which fromJson filters out on load), and for a built-in basic catalog, the published document.

      Returns Record<string, unknown>

      A fresh document that the caller may modify.

    • fromJson(
          json: Record<string, any>,
          protocolVersion?: string,
          catalogId?: string,
      ): CatalogApi

      Constructs a schema-only Catalog from an authored A2UI catalog document.

      Each entry is a JsonComponentApi or JsonFunctionApi whose model is its definition as written, from which its Zod schema is derived on first use, and the catalog keeps the document-level fields, so toJson returns the document unchanged.

      Parameters

      • json: Record<string, any>

        Raw catalog document or client capabilities inline catalog.

      • OptionalprotocolVersion: string

        Protocol version of the catalog. When given, it takes precedence over the protocolVersion the document declares: it becomes the catalog's protocolVersion and selects the version's loading rules, while toJson still writes the version the document declares. When omitted, the document's version applies, and for a document that declares none, such as those published before v1.0, DEFAULT_PROTOCOL_VERSION.

      • OptionalcatalogId: string

        Catalog ID to use instead of the one the document declares, or for a document that declares none, such as the v0.8 basic catalog. It becomes the catalog's id, and replaces the document's own catalogId in toJson; a document that declares none still has none in toJson.

      Returns CatalogApi

      A new Catalog populated with component and function schemas.

      Throws

      If the catalog ID is missing or not a string.

      Throws

      If a v1.0 catalog has a $ref to a document other than itself or common_types.json, such as another catalog. Such a reference is never fetched.
